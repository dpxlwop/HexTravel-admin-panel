# ТЗ на веб-админ-панель HexTravel

Разработай русскоязычную панель для администраторов HexTravel. Основной сценарий — войти, открыть раздел «Цифровизация туров», создать черновик в глобальном каталоге, заполнить маршрут и опубликовать тур. Администратор может открыть уже сохранённый тур из списка и продолжить работу.

## Стек и контракт

- Обязательный стек — **TypeScript, React и `liquid-glass-react`**. Используй TypeScript в режиме `strict`. Сборщик, роутер и библиотеку форм выбери по необходимости. Зафиксируй версии зависимостей в lockfile. [Документация `liquid-glass-react`](https://github.com/rdev/liquid-glass-react)
- Источник API для проекта — предоставленный `api-docs.json` (HexTravel API 1.0.0, OpenAPI 3.1.0). Используй его для маршрутов, типов запросов, ответов и доступных операций. Ограничения, которые Swagger не отобразил, сверяй с DTO и контроллерами `HexTravel-BD-Java`. При расхождении фиксируй конкретный endpoint и фактическое поведение в README.
- Панель работает с REST Gateway. Базовый URL настраивается для стенда. При размещении на одном origin достаточно `/api/v1`. Сгенерированный `servers` из OpenAPI служит метаданными. Предоставь `.env.example` с публичными параметрами конфигурации.

## Вход и навигация

1. На экране входа покажи поля «Логин или email» и «Пароль». Вызови `POST /api/v1/auth/login` с `LoginWebRequest` (`login`, `password`). Сохрани полученные `accessToken` и `refreshToken` в памяти приложения. Перезагрузка страницы требует повторного входа. После входа можно вернуться к сохранённому черновику.
2. Доступ к панели — для `ADMIN`. Для выбора экрана используй claim `role` в access JWT. Решение о доступе к операциям принимает Gateway. Для защищённых запросов передавай `Authorization: Bearer <accessToken>`. При входе под `USER` заверши локальную сессию и покажи «Для входа нужна роль администратора».
3. На `401` от защищённого запроса используй `POST /api/v1/auth/refresh` с `refreshToken`. Объедини параллельные запросы обновления в один, замени пару токенов и повтори исходный запрос один раз. При отказе обновления верни на вход. Кнопка «Выйти» отзывает refresh-токен через `POST /api/v1/auth/logout` и завершает локальную сессию.
4. После входа открой «Главную». Для первой версии достаточно заголовка и навигации. В боковой панели размести «Главная» и «Цифровизация туров», в меню аккаунта — «Выйти». На узком экране боковая навигация раскрывается кнопкой в верхней панели.

## Список, черновик и публикация

1. В разделе «Цифровизация туров» покажи список из `GET /api/v1/trips`. В каждой строке выведи название, даты и состояние публикации по `isPublic` («Черновик» или «Опубликован»). Предусмотри кнопку «Создать тур», открытие строки и состояния загрузки, пустого списка и ошибки.
2. На экране создания открой карточку и покажи разделы редактора. Первое действие «Сохранить черновик» проверяет обязательные поля карточки и вызывает `POST /api/v1/trips` с `isPublic: false`. После `201` используй возвращённый `id`, открой постоянный адрес редактора и разреши сохранение вложенных записей. Все разделы доступны на этом же экране. Вложенные записи сохраняются отдельными действиями в соответствующих разделах.
3. При повторном открытии получи карточку через `GET /api/v1/trips/{tripId}` и загрузи связанные данные соответствующих разделов. «Сохранить изменения» отправляет изменённые поля карточки через `PATCH /api/v1/trips/{tripId}`. Черновики продолжают храниться на сервере. Для опубликованного тура поясни рядом с действием, что сохранённые изменения будут видны в каталоге.
4. «Опубликовать» — отдельное действие для черновика. Сначала предложи сохранить незавершённые правки. После успешного сохранения отправь `PATCH /api/v1/trips/{tripId}` с `{"isPublic":true}`. Обнови строку списка и состояние редактора после подтверждения от API. Публикация доступна с пропущенными необязательными разделами.
5. `status` отражает состояние поездки (`PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`). Состояние публикации определяется отдельно через `isPublic`. При создании можно предвыбрать `PLANNED` с возможностью изменить.

## Редактор тура

Разделы редактора — «Основное», «Точки маршрута», «Программа», «Транспорт», «Бронирования», «Фото». Программа по дням и событиям, транспорт и детали рейсов, бронирования и галерея добавляются по желанию. При пустом разделе предложи «Добавить» и возможность явно выбрать «Не добавлять». Для уже сохранённых записей доступны просмотр и документированные операции с конкретной записью.

| Форма | Обязательные поля при добавлении | Необязательные поля и особенности |
| --- | --- | --- |
| Карточка (`TripCreateRequest`) | `title`, `coverImageUrl`, `startDate`, `endDate`, `status`, `currency` | `description`, `startLat`, `startLng`, `endLat`, `endLng`, `budget`. `isPublic` задаётся действиями черновика и публикации. URL обложки нужен и при пустой галерее. `currency` передаётся и при пропущенном бюджете. |
| Точка (`TripPointCreateRequest`) | `name`, `orderIndex`, `pointType`, `latitude`, `longitude`, `address`, `placeId` | `description`, `arrivalTime`, `departureTime`, `durationHours`. `orderIndex` — целое от 0, уникальное в пределах тура. Покажи точки в порядке `orderIndex`, предложи следующий свободный индекс новой точке. |
| День (`ItineraryDayCreateRequest`) | `dayNumber`, `date`, `title` | `notes`. Номер дня — положительное целое. Открывай события внутри выбранного дня. |
| Событие (`ItineraryEventCreateRequest`) | `title`, `startTime`, `endTime`, `orderIndex`. Сохранённые `dayId` и `tripPointId` передаются в пути запроса | `description`. Точку выбирай из маршрута этого тура. `startTime` и `endTime` — локальное время `HH:mm:ss`. |
| Транспорт (`TransportCreateRequest`) | `transportType`, `company`, `vehicleNumber`, `departureTime`, `arrivalTime`, `currency` | `durationHours`, `ticketPrice`, `notes`. Используй поля схемы каталожного транспорта. |
| Рейс (`FlightCreateRequest`) | `airline`, `flightNumber`, `departureAirport`, `arrivalAirport`, `terminalDeparture`, `terminalArrival`, `baggageAllowance`, `seatNumber` | Весь блок рейса опционален. Он привязывается к сохранённому транспортному отрезку через `transportId`. Коды аэропортов состоят из трёх заглавных латинских букв. |
| Бронирование (`BookingCreateRequest`) | `placeId`, `bookingType`, `status`, `checkIn`, `checkOut`, `guestsCount`, `totalPrice`, `currency`, `confirmationNumber` | `notes`. `confirmationNumber` — телефон клиента для подтверждения бронирования, строка из 10–15 цифр с возможным `+` в начале. `guestsCount` больше 0, `totalPrice` от 0. |
| Фото (`PhotoCreateRequest`) | `tripId` из редактора и файл на отдельном шаге загрузки | `placeId`, `tripPointId`, `caption`, `latitude`, `longitude`, `takenAt`, `isPublic`. `caption` до 500 символов. Поле `isPublic` фото задаётся отдельно, по умолчанию `false`. |

### Правила ввода и редактирования

- Обязательные поля внутри выбранного блока валидируй по DTO. Для необязательного поля используй чекбокс «Не указывать» или равнозначный контроль с явным состоянием. При выборе этого состояния поле ввода скрывается или выключается, ключ при создании пропускается. Если администратор включил ввод поля, проверь введённое значение. Сохраняй допустимые `0` и `false`.
- В `PATCH` передавай изменённые значения. Пропуск поля сохраняет серверное значение. Опцию очистки ранее сохранённого значения показывай только при подтверждённой семантике очистки API. Для значений без поддержки очистки доступна замена. Удаление вложенной записи — отдельное действие с подтверждением.
- Для готовых точек, дней, событий, отрезков, рейсов и бронирований контракт предусматривает чтение, добавление и удаление. Содержимое новой записи можно исправить до отправки. Работу с сохранёнными записями ограничивай этим набором операций. Перед удалением покажи зависимые записи, которые оно затронет, если API возвращает связанное содержимое. При конфликте или наличии связей покажи причину и сохрани форму.
- `date` отправляй как `YYYY-MM-DD`, `date-time` — как ISO 8601 со смещением. У полей `date-time` показывай используемую временную зону. Соблюдай правила будущих дат из DTO. Для тура `endDate >= startDate`. Для пары времени в точке маршрута отбытие должно быть не раньше прибытия. `LocalTime` событий передавай без смещения. `currency` соответствует `[A-Z]{3}`.
- У полей с перечислением используй заданные API значения. Если схема определяет строку, Swagger-пример служит подсказкой. Диапазоны координат — широта от −90 до 90 и долгота от −180 до 180. Бюджет и цена билета допускают 0. `durationHours` точки должно быть больше 0, у транспорта допустим 0. Сортируй дни по `dayNumber`, события внутри дня по `orderIndex`.

### Поиск и создание места

1. В форме точки реализуй общий компонент выбора места с режимами поиска «По OSM ID» и «По ID места». Этот же компонент можно использовать для бронирований и привязки фото к месту. Вызови `GET /api/v1/places/by-osm-id/{osmId}` для OSM ID или `GET /api/v1/places/{id}` для UUID места. В форме показывай найденные название, адрес и координаты.
2. При выборе места подставь в точку `placeId` из `PlaceResponse.id`, а также предложи название, адрес, широту и долготу из ответа. При поиске по `osmId` сохраняй в точке именно UUID HexTravel. Ввод OSM ID должен сохранять точное целое значение формата `int64`.
3. После `404` предложи «Создать место» в диалоге поверх формы. Сохрани введённые данные точки при переходе и верни фокус в редактор при закрытии диалога. При поиске по OSM ID перенеси введённый ID в форму места. При поиске по UUID для создания потребуется заполнить реальный `osmId`.
4. Для `POST /api/v1/places` обязательно собери `name`, `osmCategory`, `osmValue`, `latitude`, `longitude`, `address`, `city`, `country`, положительный `osmId` и `osmTags`. `osmTags` — строка, содержащая JSON-объект. Для отсутствующих OSM-тегов отправь строку `"{}"` по контракту. Предусмотри необязательные `description`, `rating`, `reviewsCount`, `phone`, `website`, `openingHours`, `imageUrl`, `tags`.
5. После `200` выбери созданное место в исходной форме и используй возвращённый `id`. Если создание вернуло `409`, повтори `GET` по `osmId` и предложи использовать найденное место. При ошибке запроса кроме `404` покажи ошибку и повтор поиска.

### Галерея

- Сначала создай запись через `POST /api/v1/me/photos` с `tripId` и выбранными метаданными. Затем отправь файл через `POST /api/v1/me/photos/{photoId}/file`, где `photoId` взят из ответа. Используй `FormData` с частью `file` и позволь браузеру установить multipart boundary. Ответ загрузки может быть текстовым.
- Список загружай через `GET /api/v1/me/photos/trip/{tripId}`. Для превью запрашивай файл через `GET /api/v1/me/photos/{photoId}/file` с Bearer-токеном и отображай через Blob URL. Освобождай Blob URL после использования. Для формата, который браузер не отображает, покажи возможность скачать файл.
- При сбое загрузки сохрани `photoId` и состояние «Файл не загружен». Повторяй загрузку для существующего `photoId`. При повторном открытии редактора отмечай запись, если метаданные существуют, а `GET` файла возвращает `404`. В редакторе должна быть возможность удалить запись через `DELETE /api/v1/me/photos/{photoId}`. Перед отправкой проверяй лимит целевого стенда и допустимое расширение (`jpg`, `jpeg`, `png`, `heic`, `webp`, `gif`, `bmp`, `tiff`). В конфигурации HexTravel Nginx ограничивает multipart-запрос 10 МиБ, а Gateway — файл 20 МиБ. Покажи понятную ошибку на `413`.

## REST-операции редактора

Ниже `T` обозначает `/api/v1/trips/{tripId}`.

| Объект | Чтение | Создание, обновление и удаление |
| --- | --- | --- |
| Каталог и карточка | `GET /api/v1/trips`, `GET T` | `POST /api/v1/trips` (201), `PATCH T` (200) |
| Точки маршрута | `GET T/points`, `GET T/points/{id}` | `POST T/points` (201), `DELETE T/points/{id}` (204) |
| Дни | `GET T/days` | `POST T/days` (201), `DELETE T/days/{id}` (204) |
| События | `GET T/days/{dayId}/events` | `POST T/days/{dayId}/{tripPointId}/events` (201), `DELETE T/days/{dayId}/events/{id}` (204) |
| Транспорт | `GET T/transports`, `GET T/transports/{id}` | `POST T/transports` (201), `DELETE T/transports/{id}` (204) |
| Рейс | `GET T/transports/{transportId}/flight` | `POST T/transports/{transportId}/flight` (201), `DELETE T/transports/{transportId}/flight/{flightId}` (204) |
| Бронирования | `GET T/bookings`, `GET T/bookings/{id}` | `POST T/bookings` (201), `DELETE T/bookings/{id}` (204) |

## Ошибки и состояние формы

- Во время запроса блокируй повторную отправку действия. Подтверждай сохранение после успешного ответа. При частичном сбое сохраняй введённые значения, ID уже созданных сущностей и результат успешно сохранённых операций. Сетевой сбой после отправки `POST` требует сверки с сервером перед повтором.
- Покажи понятные состояния для `400` (ошибка данных), `401` (сеанс), `403` (роль), `404` (объект недоступен), `409` (конфликт), `413` (слишком большой файл), `428` (связанные записи, когда это документировано) и для сетевого сбоя или `5xx`. Используй `ErrorResponse.error` и `ErrorResponse.message` при наличии, с запасным сообщением на случай пустого ответа или ответа без JSON. `204` обрабатывай как успех без тела.
- При конфликте тура по названию и датам покажи сообщение и предложи вернуться к списку или изменить данные. После ошибки конкретного раздела оставляй открытым этот раздел. При уходе со страницы с несохранёнными правками покажи диалог подтверждения.
- Держи пароли и JWT вне журналов, URL и постоянных хранилищ браузера. Номер телефона из бронирования и номер места пассажира показывай в нужных формах админ-панели по контракту. Исключи эти данные из диагностических журналов и аналитики. [OWASP HTML5 Security](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)

## Критерии приёмки

- `ADMIN` входит, попадает на главную и открывает «Цифровизацию туров». `USER` видит отказ в доступе. Истечение access-токена обрабатывается обновлением сессии или повторным входом.
- Сохранение валидной карточки создаёт черновик в глобальном каталоге. После перезагрузки и входа черновик открывается из списка. Изменения карточки сохраняются через `PATCH`.
- В черновике можно добавить и проверить порядок нескольких точек. Поиск места работает по OSM ID и UUID. После `404` можно создать место в диалоге и использовать возвращённый UUID. Отмена диалога сохраняет введённые данные.
- Можно пропустить все четыре дополнительных раздела и опубликовать тур с карточкой и точками. Если раздел включён, его обязательные поля действуют. Отдельно проверь добавление дня с событием, транспорта с рейсом, бронирования и фото.
- После публикации тур показан как «Опубликован», а чтение каталога по API под `USER` возвращает его. До публикации черновик доступен `ADMIN`.
- Сбой загрузки фото после создания метаданных допускает повтор без новой записи. На конфликт, отказ API и превышение лимита форма отвечает сообщением, которое позволяет продолжить работу.
- Основной сценарий работает в Safari и Chromium, включая узкий экран и навигацию клавиатурой.
